Идея проекта

Перед сдачей агент и человек сверяются с чек-листом из README глазами. Пропущенный обязательный файл или сломанная рубрика обнаруживаются на защите. rubrica превращает чек-лист в машинную проверку с кодом возврата, который одинаково понимают человек, агент и CI.

make install          # venv + зависимости
sh scripts/check.sh   # проверки кода: compileall + 74 теста
make audit            # аудит папки сдачи по рубрике
opencode mcp list     # rubrica connected
Фича A
Валидация входа. Плохой вход отклоняется до чтения файлов сдачи и до любого сетевого вызова.
Фича B
Отказ LLM-зависимости не меняет вердикт аудита. Появляется код 3 и отдельное поле narrative_error.
Среда
Четыре подключения, каждое закрывает свой шаг задачи. Подробности — ниже.

Фича A — валидация входа

Аудит не начинается, пока не пройдены дешёвые локальные проверки. До этого момента ни одного чтения файла сдачи и ни одного сетевого запроса.

Отклоняется, еслиПочему это важно
путь пустой, не существует или не папканет смысла аудитовать
путь указывает на корень ФС или ..защита от «прошёл не по той папке»
в папке > 5000 файлов или > 64 МБпризнак, что аудитируется не сдача
рубрика — не YAML, пуста или структурно невернаиначе аудит бессмысленен

Рубрика проверяется целиком: все проблемы приходят одним списком, а не по одной за запуск.

$ .venv/bin/python -m rubrica.cli /no/such/dir
ОТКАЗ: вход не прошёл валидацию: папка /no/such/dir не существует
EXIT=2

→ src/rubrica/validate.py (валидация входа) → src/rubrica/spec.py (валидация рубрики) → tests/test_validate.py → tests/test_spec.py

Фича B — деградация при отказе зависимости

Отчёт можно обогатить текстовой рецензией от внешнего OpenAI-совместимого endpoint. Отказ зависимости не имеет права изменить вердикт аудита — ни баллы, ни exit_code, ни findings.

Граница между фичами проходит по файлам: core.py не содержит ни одного сетевого вызова, вся работа с внешним миром живёт в narrative.py.

Среда агента: зачем какое подключение

ПодключениеКакой шаг задачи улучшаетПодтверждение
AGENTS.md задаёт контракт, runner и границы до первой правки; агент назвал docs/requirements.md и sh scripts/check.sh по содержанию файла, а не выдумал E1, E5
skill submission-audit шаг «что ещё не сдано»: одна команда вместо ручного прохода по чек-листу, с приоритетом блокеров E1, разбор
MCP rubrica_audit узнать вердикт прямо из чата, без второго терминала; ответ структурирован, агент может сразу править файлы E2
hook check-after-edit убирает шаг «не забудь прогнать проверку»: runner запускается по событию правки, результат возвращается агенту E3, E5
Почему подключений ровно четыре. Каждое закрывает свой шаг: правила — границы, skill — процедуру, MCP — способ узнать вердикт, hook — автоматическую проверку. Количество подключений само по себе не даёт ничего: четвёртое подключение (например, references как в Claude Code) я бы добавил только при реальном дефиците контекста. Не добавлял.

Свой MCP: rubrica_audit

Один tool, локальный stdio-сервер. MCP-слой отвечает только за формат ответа и понятную ошибку — правила, веса и поиск секретов живут внутри rubrica.

MCPServer "rubrica"
  └── tool rubrica_audit(target, spec="")
        ├── validate_all(...)      фича A
        ├── load_spec(...)
        ├── audit(spec, target)    ядро
        └── fix_hints(report)

Деталь, которая стоила переделки. Первая версия бросала ValueError. Opencode показывал агенту Error executing tool rubrica_audit — без причины, и агент сделал вывод, что сервер не подключён. Ошибка возвращается данными, а не исключением: только так причина доходит до агента.

Hook: check-after-edit

Подписывается на tool.execute.after и после каждой правки в src/, tests/, mcp/ запускает scripts/check.sh, дописывая вывод в результат того же инструмента.

apply_patch → «Success. Updated the following files: …»
            + ── check-after-edit: FAIL (exit 1) · scripts/check.sh после apply_patch: tests/test_core.py
              ..................F..............................................
              FAIL: test_weights_sum_into_score
              AssertionError: 5 != 7
              FAILED (failures=1)
              Проверка красная. Runner под зелёный результат не трогаем
              (docs/style-guide.md, правило 4) — чинится код.

В потоке сессии нет отдельного вызова bash sh scripts/check.sh: проверку запустил hook.

Три дефекта, найденных на реальных прогонах. 1. Плагин вообще не загружался: строка комментария, начавшаяся с * вне блока комментария, роняла модуль при импорте — молча, без ошибки в логах.
2. Hook не замечал apply_patch: там нет filePath, только patchText, а пути приходят относительными.
3. В отчёт попадал только stdout, а unittest пишет в stderr — агент видел «проверка прошла» при падающем тесте.

→ .opencode/plugins/check-after-edit.js → docs/HOOK.md

Подтверждения применения

Не «файл существует», а реальные вызовы инструментов из потоков opencode run --format json. Сырые потоки — в evidence/raw/.

ФайлЧто подтверждает
E1 в одной сессии: read AGENTS.md → skill submission-audit → read references/rubric-rules.md → rubrica_audit с реальным JSON
E2 свой MCP: корректный вызов и два разных ошибочных входа с текстом причины
E3 hook после правки возвращает агенту FAIL с трейсом упавшего теста
E4a агент прочитал правило 4 и всё равно подогнал production-код под неверный тест — PASS, но код сломан
E5 тот же сценарий с явным указанием на правило: агент откатал неверный тест, hook дал PASS
E6 фича B: четыре живых сценария, вердикт аудита не меняется при отказе зависимости
raw-B сессия агента в worktree: реализация по требованиям + три дефекта, найденных человеком
E7 handoff: новая сессия восстанавливает состояние и сверяет его с фактическим прогоном

Рефлексия: коротко

  • Помогло: runner как единственная точка проверки — у агента не осталось выбора, что запускать; ошибка как данные, а не как исключение (иначе агент не видит причину).
  • Помогло с оговоркой: правило 4 в style guide. Агент его прочитал и нарушил. Помогло не правило, а то, что человек увидел diff. Проверка умеет сказать «зелёно», но не умеет сказать «правильно».
  • Мешало: установлен opencode 1.18.30, а слайды рассчитаны на 2.0.20 — API плагина другой; MCP SDK для Python различается между ветками (FastMCP против MCPServer).
  • Дороже всего: диагностика невидимых дефектов hook'а. «Плагин лежит в правильной папке» и «плагин работает» — разные утверждения.
  • Вмешивался: трижды — на зелёную проверку со сломанной семантикой, на тест, уходивший в сеть, и на умолчания, указывающие на чужой API.
