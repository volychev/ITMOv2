# SDD-фреймворки: GitHub Spec Kit и OpenSpec

Сравнение по одной и той же фиче — автономный HTML-отчёт `rubrica --html PATH`.
Spec Kit 1.2.5 использован как основной процесс; OpenSpec 1.14.1 прогнан
отдельно на baseline-коммите `c7c60a5`, чтобы сравнение опиралось на реальные
артефакты, а не на презентации. Транскрипт и копии артефактов OpenSpec лежат в
[`evidence/openspec-baseline/`](../evidence/openspec-baseline/transcript.txt).

## Коротко

| | GitHub Spec Kit 1.2.5 | OpenSpec 1.14.1 |
|---|---|---|
| Вход | `specify init --ai opencode` | `openspec init --tools opencode` |
| Единица работы | feature `specs/001-html-report/` | change `openspec/changes/html-report/` |
| Главный артефакт | `spec.md` с user stories, FR, SC | delta-spec с `ADDED/MODIFIED/REMOVED` |
| Планирование | `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, `contracts/` | `design.md`, `tasks.md` |
| Проверка | промпты `analyze`/`checklist`, скрипты предусловий | `openspec status`, `openspec validate --strict` |
| Жизненный цикл | спека фичи живёт рядом с кодом | change архивируется и вливается в `openspec/specs/` |
| Больше подходит | новая фича, много контекста и решений | поток изменений в уже описанной системе |

## Что было сделано

### Spec Kit

1. `specify init` создал `.specify/` (шаблоны, скрипты, конституция) и
   `.opencode/commands/speckit.*`.
2. Конституция зафиксировала границы проекта: не менять ядро аудита, проверять
   через публичный интерфейс, не добавлять зависимости.
3. `create-new-feature.sh` создал `specs/001-html-report/`.
4. Две «команды» — UI и логика — независимо написали `spec-before.md`. Затем
   спеки сведены в общий контракт `contracts/ui-logic.md`, после чего появились
   `spec-after.md` и консолидированная `spec.md`.
5. `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, `tasks.md` и
   `checklists/requirements.md` довели замысел до задач T001–T038.
6. Реализация шла по задачам: тесты → падение → код → `scripts/check.sh`.

### OpenSpec

1. `openspec init --tools opencode --language ru` создал `openspec/` и
   команды/скиллы OpenCode.
2. `openspec new change html-report` создал change с пустым `.openspec.yaml`.
3. `openspec status` показал граф артефактов: `proposal` → `specs`/`design` →
   `tasks`; незаполненные артефакты помечены как заблокированные.
4. `openspec instructions <artifact>` выдал для каждого шага отдельную
   инструкцию и шаблон.
5. Заполнены `proposal.md`, delta-spec `specs/html-report/spec.md`,
   `design.md`, `tasks.md`.
6. `openspec validate html-report --strict` прошёл: 4/4 артефакта, сценарии
   WHEN/THEN, ни одного предупреждения.

## Различия, которые почувствовались

### 1. Спека как продукт против спеки как изменения

Spec Kit составляет описание возможности «с нуля»: user stories с приоритетами,
функциональные требования `FR-###`, критерии успеха `SC-###`, edge cases. Это
удобно, когда нужно договориться о продукте и показать полноту.

OpenSpec мыслит дельтами: `## ADDED Requirements`, `## MODIFIED Requirements`,
`## REMOVED Requirements`. Спека — не документ фичи, а патч к уже существующей
возможности. Для brownfield это точнее: видно, что именно меняется, а архив
сливает дельту в основную спеку.

### 2. Жёсткость процесса

У Spec Kit процесс держится на промптах и дисциплине: `analyze` и `checklist`
— это команды агенту, а не валидатор. Консистентность (нет ли FR без задачи,
нет ли задачи без требования) мы проверяли отдельным проходом и арифметикой:
31 FR, 9 SC, нет битых ссылок и placeholder'ов.

OpenSpec валидирует структуру кодом: `status` не даст заполнить `tasks` раньше
`specs`, `validate --strict` проверяет дельты, сценарии и длину описаний. Это
снимает часть ручной сверки, но и пространства для манёвра меньше.

### 3. Две команды и общий контракт

Ни один из фреймворков не умеет «две команды» из коробки. Spec Kit ближе к
этому: user stories и `[P]`-задачи естественно делятся по зонам
ответственности. Мы эмулировали команды субагентами: каждый написал свою спеку
до общего контракта, а расхождения (кто владеет путём, что делать с
`--max-findings`, какой код при ошибке записи) разрешались в
`contracts/ui-logic.md`.

OpenSpec мыслит возможностями (`capability`), а не командами. Его дельта-спека
описывает поведение целиком: в baseline получилось 9 требований и 13 сценариев,
и параллельная работа двух команд в одном change быстрее приводит к конфликту
правок. Для нашей задачи пришлось бы либо делить change на два, либо вручную
держать тот же контракт.

### 4. Планирование

Spec Kit даёт больше слоёв: `research.md` фиксирует альтернативы, `data-model.md`
— сущности, `quickstart.md` — сценарии приёмки, `contracts/` — интерфейс.
Это полезно, когда решений много и они дороги.

OpenSpec компактнее: `design.md` отвечает на «как», `tasks.md` — на «в каком
порядке». Для небольшой фичи этого достаточно; для большой не хватает места
под исследование и модель данных, и оно уходит в `design.md` вручную.
### 5. Задачи и трассировка

Оба фреймворка требуют проверяемые задачи. Spec Kit группирует их по фазам и
user stories, помечает `[P]` и `[US*]`; в нашем `tasks.md` 38 задач с
зависимостями и checkpoint'ами. OpenSpec требует, чтобы у каждой задачи была
проверка, и группирует по инкрементам; получилось 17 задач в четырёх группах.

Трассировка в Spec Kit богаче за счёт `FR/SC → US → task`. В OpenSpec она
короче: требование → сценарий → задача, без отдельной нумерации требований.

### 6. Инструментальная база

Spec Kit — это bash-скрипты и markdown-команды, без обязательного рантайма.
OpenSpec — Node CLI с состоянием, графом артефактов и валидатором; ему нужен
Node и `npm`.

Для проекта без Node Spec Kit дешевле. Для команды, которая хочет проверяемый
процесс в CI, OpenSpec даёт больше готового.

## Что совпало

- Оба начинают с «зачем» и отделяют поведение от реализации.
- Оба требуют явных сценариев и проверяемых критериев.
- Оба плохо переносят молчаливые допущения: расхождения всплывают на стыке
  спеки и кода.
- В обоих случаях качество результата определил общий контракт, а не формат
  файлов. Фреймворк лишь заставил зафиксировать его до кода.

## Выводы

- Для **новой фичи с большим пространством решений** (как HTML-отчёт) Spec Kit
  удобнее: конституция, research, data-model и quickstart дают контекст, который
  иначе пришлось бы держать в голове.
- Для **потока изменений в существующей системе** OpenSpec точнее: дельты,
  архив и `validate --strict` не дают спеке разъехаться с кодом.
- Для **двух параллельных команд** решающим оказался не фреймворк, а
  письменный контракт. Если бы мы выбрали OpenSpec, контракт всё равно
  понадобился бы — просто в другом месте.
- Следующий разумный шаг для проекта — держать долгоживущее описание
  возможностей в OpenSpec-подобном виде, а крупные фичи планировать через
  Spec Kit. Смешивать их в одном репозитории без нужды не стоит: два источника
  правды быстро разойдутся.
