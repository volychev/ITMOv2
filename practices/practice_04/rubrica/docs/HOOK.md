# Hook: check-after-edit

Файл: [`../.opencode/plugins/check-after-edit.js`](../.opencode/plugins/check-after-edit.js).
Подключается автоматически: opencode 1.18.30 подхватывает любой `*.js` в
`.opencode/plugins/` при старте, отдельной записи в `opencode.json` не нужно.

## Что делает

Подписывается на `tool.execute.after`. После каждой правки файла в
`src/rubrica/`, `tests/` или `mcp/rubrica_mcp/` запускает
`sh scripts/check.sh` и дописывает вывод в результат того же инструмента,
которым сделана правка.

```
apply_patch → «Success. Updated the following files: …»
            + ── check-after-edit: FAIL (exit 1) · scripts/check.sh после apply_patch: tests/test_core.py
              == rubrica: проверки ==
              compileall: ok
              ..................F..............................................
              FAIL: test_weights_sum_into_score
              AssertionError: 5 != 7
              Ran 65 tests in 0.222s
              FAILED (failures=1)
              Проверка красная. Runner под зелёный результат не трогаем
              (docs/style-guide.md, правило 4) — чинится код.
```

Агент видит вердикт рядом со своим диффом. Отдельный вызов
`bash sh scripts/check.sh` не нужен — в потоке сессии его нет, см.
[`../evidence/E3-hook-fail.md`](../evidence/E3-hook-fail.md).

## Зачем он нужен

Без hook'а шаг «прогони проверку после правки» остаётся на агенте. Он то
пропускает его, то прогоняет три раза подряд. Hook убирает решение: проверка
происходит всегда, потому что событие уже произошло.

## Три дефекта, найденных при настройке

Все три найдены на реальных прогонах, а не при чтении кода.

### 1. Плагин не загружался вообще

В файле осталась строка комментария, начинающаяся с ` * `, вне блока
комментария:

```js
// в opencode 1.18.30 правка в основном идёт через apply_patch, и хук,
 * который слушает только edit/write, молча пропускает половину правок.
```

Строка `* который слушает…` парсилась как бинарная операция, модуль падал при
импорте, и opencode молча продолжал работу без плагина. Ни ошибки в логах, ни
следа. Нашлось бисекцией файла: при load по кускам сбой воспроизводился ровно
на этой строке.

Урок: «плагин лежит в правильной папке» и «плагин работает» — разные
утверждения. Проверяется только реальным вызовом правки.

### 2. Hook не замечал `apply_patch`

Первый вариант слушал `edit` и `write`. Агент в opencode 1.18.30 правит файлы
через `apply_patch`, и в его аргументах нет `filePath` — только `patchText`.
Хук молча пропускал все правки.

Исправлено: список инструментов расширен (`edit`, `write`, `patch`,
`apply_patch`, `multiedit`), а пути извлекаются из `patchText`. Отдельно
пришлось нормализовать относительные пути: `apply_patch` передаёт
`tests/test_core.py`, а `edit` — абсолютный путь, и фильтр на `/tests/`
просто не срабатывал на относительных.

### 3. В отчёт попадал только stdout

`unittest` пишет свой отчёт в stderr. Вариант `(stdout || stderr)` при
работающем stdout показывал агенту `compileall: ok` и обрывал вывод, то есть
сообщал «проверка прошла» при падающем тесте. Исправлено на склейку обоих
потоков.

## Границы

Hook не блокирует инструмент и ничего не чинит. Он только сообщает. Решение
принимает агент или человек. Это осознанный выбор: блокирующий hook
мешал бы агенту делать промежуточные правки в несколько шагов.

## Чего hook не может

Проверка не различает «правильно починил» и «подогнал под зелёный результат».
Два прогона в [E4a](../evidence/E4a-wrong-fix-detected.md)
и [E5](../evidence/E5-hook-pass-by-rule.md) дали одинаковый PASS, хотя один
сломал семантику `max_score`, а второй откатил неверный тест. Различает их
только чтение diff человеком.

## Проверка вручную

Runner обязан работать без hook'а — иначе приёмка невозможна:

```sh
sh scripts/check.sh
```

Hook лишь вызывает эту команду. Ничего, кроме неё, он не добавляет в процесс.
