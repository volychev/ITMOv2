# Feature Specification: Автономный HTML-отчёт аудита

**Feature Branch**: `001-html-report`

**Created**: 2026-11-02

**Status**: Draft — ожидает приёмки человеком до реализации

**Input**: «Добавить в CLI `rubrica` необязательный флаг `--html PATH`, который
генерирует автономный HTML-отчёт аудита с поиском, фильтром по severity,
переключателем „только провалы“, сортировкой и сбросом. Отчёт открывается
офлайн, без внешних CSS/JS/шрифтов».

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Сгенерировать и открыть отчёт (Priority: P1)

Студент или преподаватель запускает аудит и получает один HTML-файл, который
можно открыть офлайн, приложить к сдаче или показать на защите. Содержимое
файла совпадает с тем же аудитом в JSON: баллы, находки, предупреждения,
опциональная рецензия.

**Why this priority**: без самого артефакта остальные действия (поиск, фильтр,
сортировка) не имеют смысла. Это минимальный полезный результат фичи.

**Independent Test**: запустить `rubrica <target> --spec <rubric> --html
/tmp/report.html` на валидной сдаче, открыть файл в браузере без сети,
сверить `score/max_score`, `passed/failed/blockers` и rule id с `--json`.

**Acceptance Scenarios**:

1. **Given** валидная папка сдачи и валидная рубрика, **When** запускаю
   `rubrica <target> --html /tmp/report.html`, **Then** файл создан, stdout —
   прежний текстовый отчёт, stderr содержит `HTML-отчёт: /tmp/report.html`,
   код возврата совпадает с запуском без флага.
2. **Given** сдача с провалами, **When** генерирую HTML и JSON, **Then**
   значения метрик и множество rule id совпадают, порядок находок — порядок
   рубрики.
3. **Given** `--json --html`, **When** запускаю команду, **Then** stdout —
   валидный JSON прежней схемы, HTML — отдельный файл, подтверждение в stderr.
4. **Given** ошибка пути `/nope/report.html`, **When** запускаю команду,
   **Then** код 2, файл не создан, аудит не запускался.

---

### User Story 2 — Найти нужную находку (Priority: P2)

Человек открывает отчёт, чтобы быстро ответить: «что именно провалено и где».
Он ищет по rule id, заголовку и деталям, фильтрует по severity, оставляет
только провалы, меняет сортировку и сбрасывает фильтры.

**Why this priority**: HTML без навигации по 200 правилам почти бесполезен;
это главная причина делать интерактивный отчёт вместо ещё одного текста.

**Independent Test**: открыть отчёт с ≥ 5 находками, ввести запрос, переключить
severity, включить «только провалы», сменить сортировку и нажать «Сбросить».

**Acceptance Scenarios**:

1. **Given** отчёт открыт, **When** ввожу `readme`, **Then** остаются находки,
   где `readme` есть в rule id, заголовке или деталях без учёта регистра;
   счётчик показывает `Показано N из M`.
2. **Given** выбрано `severity=blocker` и включено «только провалы», **When**
   смотрю список, **Then** показаны только проваленные blocker-находки;
   фильтры комбинируются по AND.
3. **Given** активны фильтры, **When** нажимаю «Сбросить», **Then** поиск пуст,
   severity «все», «только провалы» выключено, сортировка — порядок рубрики,
   список снова полный.
4. **Given** фильтры не дают совпадений, **When** список пуст, **Then** видно
   «Ничего не найдено…», счётчик `Показано 0 из M`, метрики шапки не меняются.
5. **Given** отчёт открыт без JavaScript, **When** просматриваю страницу,
   **Then** все находки и секции читаются, фильтры не обязательны.

---

### User Story 3 — Понять вердикт и деградацию (Priority: P3)

Человек за секунду видит, всё ли прошло, есть ли блокеры и не сломалась ли
рецензия. Ошибка внешнего сервиса не должна выглядеть как провал аудита.

**Why this priority**: вердикт — главное, что читают в отчёте; но он уже
выводится в шапке, поэтому это дополнение к P1, а не отдельная фича.

**Independent Test**: сгенерировать HTML для четырёх сдач: всё прошло, провалы
без blocker, blocker, недоступная рецензия; сверить баннеры и коды возврата.

**Acceptance Scenarios**:

1. **Given** все правила прошли, **When** открываю HTML, **Then** зелёный
   баннер «Все правила пройдены», `failed=0`, `blockers=0`, код 0.
2. **Given** есть провалы без blocker, **When** открываю HTML, **Then**
   жёлтый баннер «Есть провалы без блокеров», код 1.
3. **Given** есть провал severity blocker, **When** открываю HTML, **Then**
   красный баннер «Есть блокирующие провалы», блокирующая находка выделена,
   код 2.
4. **Given** `--narrative` запрошен, но endpoint недоступен, **When** открываю
   HTML, **Then** виден бейдж «Рецензия недоступна» и текст ошибки, метрики
   не изменились; код процесса 3 (текущее поведение), включая случай блокера.

### Edge Cases

- Пустой `--html` или PATH из пробелов → отказ до аудита, код 2.
- PATH без расширения или с расширением не `.html`/`.htm` → отказ, код 2.
- PATH указывает на существующий каталог, родитель — файл, родителя нет,
  целевой файл — символическая ссылка → отказ, код 2.
- Родительские каталоги не создаются; существующий обычный файл
  перезаписывается атомарно; при ошибке старое содержимое не меняется.
- Путь внутри `target` разрешён; пробелы в PATH отчёта разрешены.
- `--max-findings` не режет HTML и JSON, только текстовый stdout.
- Одинаковый отчёт → байт-идентичный HTML (нет времени, случайных id,
  нестабильного порядка).
- Недоверенные строки `<script>`, `"><img onerror=...>` в rule id/title/detail
  отображаются как текст и не исполняются.
- Пустой отчёт (защитный случай) → «Находок нет», `0/0`, без падения.
- Нет предупреждений → «Предупреждений нет».
- «Только провалы» при полном успехе → «Провалов нет».
- Ошибка записи при уже напечатанном аудите → код 2, отчёт аудита не искажён.
- Рецензия недоступна и ошибка записи одновременно → код 2 (экспорт важнее).

## Requirements *(mandatory)*

### Functional Requirements

**CLI и совместимость**

- **FR-001**: CLI MUST принимать `--html PATH` и показывать флаг в `--help`.
- **FR-002**: Без `--html` поведение, stdout, JSON-схема и коды возврата MUST
  остаться прежними.
- **FR-003**: `--html` MUST NOT менять stdout; при успехе в stderr MUST
  печататься ровно одна строка `HTML-отчёт: <абсолютный путь>`.
- **FR-004**: `--html` и `--json` MUST быть совместимы; stdout остаётся чистым
  JSON прежней схемы.
- **FR-005**: `--max-findings` MUST ограничивать только текстовый stdout;
  JSON и HTML MUST содержать все находки.
- **FR-006**: При недоступной рецензии HTML MUST всё равно записываться,
  `narrative_error` MUST попадать в отчёт, код процесса MUST остаться 3
  (текущее поведение), а метрики аудита — не меняться.
- **FR-007**: Ошибка пути/записи HTML MUST давать код 2; ошибка записи MUST
  быть приоритетнее кода 3; отчёт аудита MUST быть напечатан, если он уже
  вычислен.

**Путь и запись**

- **FR-010**: PATH MUST быть непустым, иметь расширение `.html`/`.htm`,
  `~` MUST раскрываться, относительный путь MUST разрешаться от текущего
  каталога.
- **FR-011**: Валидация PATH MUST выполняться до чтения папки сдачи и запуска
  аудита; ошибки цели и рубрики MUST иметь приоритет.
- **FR-012**: Родительская папка MUST существовать и быть каталогом;
  родительские папки MUST NOT создаваться.
- **FR-013**: Существующий каталог и целевая символическая ссылка MUST
  отклоняться; символическая ссылка в родителях допустима.
- **FR-014**: Запись MUST быть атомарной, при ошибке старый файл MUST остаться
  неизменным, а временный файл — удалённым.
- **FR-015**: Права созданного файла MUST быть `0600`.
- **FR-016**: Путь внутри `target` MUST быть разрешён; пробелы в PATH отчёта
  MUST быть разрешены.

**Данные и рендер**

- **FR-020**: HTML MUST строиться из того же результата аудита, что текст и
  JSON; баллы, счётчики и находки MUST NOT пересчитываться.
- **FR-021**: Модель представления MUST содержать `spec_id`, `spec_title`,
  `target`, `score`, `max_score`, `passed`, `failed`, `blockers`, `exit_code`,
  `findings`, `warnings`, `narrative`, `narrative_error`.
- **FR-022**: Отчёт MUST содержать все находки в порядке рубрики; каждая
  находка MUST содержать rule id, kind, severity, ok, заголовок, детали и вес.
- **FR-023**: В отчёте MUST NOT быть даты генерации и скрытых находок;
  одинаковый вход MUST давать байт-идентичный HTML.
- **FR-024**: Текст рецензии MUST передаваться без обрезки и совпадать с JSON.
- **FR-025**: HTML MUST быть одним файлом с встроенными CSS/JS, `lang="ru"`,
  UTF-8, viewport и CSP; внешние ресурсы и сетевые запросы MUST отсутствовать.

**Экран и действия**

- **FR-030**: Шапка MUST показывать spec id/title, target, score/max, passed,
  failed, blockers, код аудита 0/1/2 и баннер вердикта.
- **FR-031**: Список MUST показывать PASS/FAIL, severity, rule id, заголовок,
  детали и вес; статус и severity MUST передаваться текстом, не только цветом.
- **FR-032**: Поиск MUST фильтровать по rule id, заголовку и деталям без учёта
  регистра, с обрезкой пробелов; ввод применяется сразу.
- **FR-033**: Фильтр severity и «только провалы» MUST комбинироваться по AND.
- **FR-034**: Сортировка MUST поддерживать порядок рубрики (по умолчанию),
  «провалы сначала», severity blocker → minor, rule id и вес (больше сначала);
  сортировка MUST быть устойчивой.
- **FR-035**: «Сбросить» MUST возвращать все контролы к значениям по умолчанию.
- **FR-036**: Счётчик `Показано N из M` MUST обновляться при каждом изменении
  фильтров и иметь `aria-live="polite" aria-atomic="true"`.
- **FR-037**: Предупреждения MUST показываться полностью; пустой список MUST
  иметь явное состояние.
- **FR-038**: Рецензия MUST иметь три состояния: не запрашивалась, получена,
  недоступна с ошибкой и пометкой «Результат аудита не изменён».
- **FR-039**: Все контролы MUST иметь подписи, быть доступны с клавиатуры,
  иметь видимый фокус; без JavaScript страница MUST оставаться полной.
- **FR-040**: Все динамические строки MUST экранироваться; динамические
  значения в атрибутах MUST быть ограничены контролируемыми значениями.

### Key Entities

- **ReportView** — неизменяемая модель для рендера: метрики аудита, все находки,
  предупреждения, рецензия и её ошибка. Не содержит времени и скрытых находок.
- **FindingView** — одна находка: rule id, kind, severity, ok, title, detail,
  weight. Порядок — порядок правил рубрики.
- **HTML-отчёт** — один самодостаточный файл; экран с шапкой, панелью действий,
  списком находок, предупреждениями и рецензией.
- **Отказ экспорта** — сообщение с путём и причиной; превращается в `ОТКАЗ`
  в stderr и код 2.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: для 100% запусков с валидным `--html` файл существует, не пуст
  и открывается офлайн в актуальном браузере.
- **SC-002**: 0 сетевых запросов при открытии отчёта по `file://`.
- **SC-003**: значения `score`, `max_score`, `passed`, `failed`, `blockers` и
  множество rule id в HTML на 100% совпадают с JSON того же запуска.
- **SC-004**: при 200 находках любое изменение фильтра или сортировки
  применяется быстрее 100 мс на офисном ноутбуке.
- **SC-005**: все пять контролов и сброс доступны клавиатурой; фокус виден.
- **SC-006**: HTML с недоверенными `<script>` и `"><img onerror=...>` не
  исполняет их и показывает как текст.
- **SC-007**: повторная генерация из одинакового отчёта даёт идентичные байты.
- **SC-008**: все сценарии отказа пути дают код 2, сообщение с путём и не
  оставляют частичный файл или temp.
- **SC-009**: все прежние тесты зелёные; `sh scripts/check.sh` проходит;
  `core.py`, `validate.py`, `spec.py`, `narrative.py` не изменены.

## Assumptions

- HTML всегда содержит полный отчёт; `--max-findings` остаётся ограничением
  только текстового stdout (как JSON уже сейчас).
- Расширение `.html`/`.htm` обязательно; молча ничего не дописывается.
- Путь отчёта задаётся явно, дефолтного имени нет; родительские папки не
  создаются; путь внутри `target` разрешён.
- Новых зависимостей нет: HTML, CSS и JS — стандартная библиотека и встроенный
  текст; поддерживаются актуальные Chrome/Firefox/Safari/Edge.
- Рецензия — обычный текст с сохранением переводов строк, без Markdown-рендера.
- Вне объёма: автооткрытие браузера, локальный сервер, графики, темы,
  сохранение фильтров между открытиями, локализация, изменение текстового и
  JSON-форматов, `--html-date`.
- Подготовка кода и приёмка — человеком; до приёмки этой спеки реализация
  не начинается.
