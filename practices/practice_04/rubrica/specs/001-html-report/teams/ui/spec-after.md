# UI-спецификация после согласования: автономный HTML-отчёт `rubrica --html`

**Фича**: [`001-html-report`](../../spec.md)
**Общий контракт**: [`contracts/ui-logic.md`](../../contracts/ui-logic.md)
**Команда**: UI (наблюдаемое поведение CLI и экрана)
**Дата**: 2026-11-02
**Статус**: Draft после согласования двух команд
**Границы**: только CLI-поверхность, экран, состояния и сквозные сценарии. Внутренние функции, модель данных и алгоритм записи — зона команды логики.

## 1. Пользовательские истории

### US-1 — Сгенерировать HTML-отчёт (P1)

Студент или преподаватель запускает аудит и получает один файл, который можно открыть офлайн и показать рядом с работой.

**Ценность**: отчёт переживает терминал, копируется в чат/архив и одинаково выглядит у всех. **Независимая проверка**: запустить `rubrica <target> --html /tmp/report.html` на валидной сдаче, открыть файл в браузере без сети и сверить баллы и находки с `--json`.

**Сценарии**:
1. **Given** валидная папка сдачи и валидная рубрика, **When** запускаю `rubrica <target> --html /tmp/report.html`, **Then** создаётся `/tmp/report.html`, stdout совпадает с запуском без флага, в stderr одна строка `HTML-отчёт: /tmp/report.html`, код возврата равен коду аудита.
2. **Given** сдача с провалами, **When** генерирую HTML, **Then** баллы, `passed/failed/blockers`, все находки и предупреждения совпадают с JSON-отчётом того же запуска.
3. **Given** путь `--html /nonexistent-dir/report.html` без родительской папки, **When** запускаю команду, **Then** файл не создаётся, аудит не запускается, в stderr есть `ОТКАЗ: HTML-отчёт не записан — …`, код 2.

### US-2 — Найти и отфильтровать находки (P2)

Человек открывает отчёт, чтобы быстро ответить: «что именно провалено и где».

**Ценность**: не приходится глазами искать по длинному списку из 200 правил.
**Независимая проверка**: открыть отчёт с ≥ 5 находками, ввести запрос, переключить severity, включить «только провалы», сменить сортировку и нажать «Сбросить».

**Сценарии**:
1. **Given** отчёт открыт, **When** ввожу `readme` в поиск, **Then** остаются только находки, где `readme` встречается в rule id, заголовке или деталях без учёта регистра; счётчик показывает `Показано N из M`.
2. **Given** выбрано `severity=blocker` и включено «только провалы», **When** смотрю список, **Then** в нём только проваленные находки severity `blocker`; фильтры применяются совместно (AND).
3. **Given** активны фильтры, **When** нажимаю «Сбросить», **Then** поиск пуст, severity `все`, «только провалы» выключено, сортировка «порядок рубрики», список снова показывает все находки.
4. **Given** фильтры не дают совпадений, **When** список пуст, **Then** показано пустое состояние и доступен сброс; итоговые метрики шапки не меняются.

### US-3 — Понять состояние аудита (P3)

Человек должен за секунду увидеть вердикт, а не вычислять его из списка.

**Ценность**: ошибка «сдал с блокером» и деградация рецензии заметны сразу.
**Независимая проверка**: сгенерировать HTML для трёх сдач (всё прошло, провалы без блокера, блокер) и для отказа рецензии; сверить баннеры и коды возврата.

**Сценарии**:
1. **Given** все правила прошли, **When** открываю HTML, **Then** виден зелёный вердикт «Все правила пройдены», `failed=0`, `blockers=0`, код аудита 0.
2. **Given** есть провалы без `blocker`, **When** открываю HTML, **Then** вердикт «Есть провалы без блокеров», код аудита 1.
3. **Given** есть провал `severity=blocker`, **When** открываю HTML, **Then** вердикт «Есть блокирующие провалы», блокирующие находки выделены, код аудита 2.
4. **Given** `--narrative` запрошен, но endpoint недоступен, **When** открываю HTML, **Then** виден блок «Рецензия недоступна» с текстом ошибки и пометкой, что результат аудита не изменён; код процесса 3, метрики прежние.
5. **Given** блокер и недоступная рецензия одновременно, **When** смотрю HTML, **Then** код аудита 2, бейдж «Рецензия недоступна», код процесса 3 — текущее поведение сохранено.

## 2. CLI-контракт

```text
rubrica <target> [--spec PATH] [--json] [--max-findings N] [--narrative]
                 [--model ID] [--timeout SECONDS] [--html PATH]
```

`--html PATH` — необязательный экспорт. Это не режим вывода, а дополнительный артефакт: stdout не меняется.

| Комбинация | Поведение |
|---|---|
| `--html PATH` | Текст в stdout как без флага; HTML записан; подтверждение в stderr. |
| `--html PATH --json` | Разрешено. В stdout — только валидный JSON прежней схемы, без новых полей; HTML — отдельный файл; подтверждение в stderr. |
| `--html PATH --narrative` | Рецензия или её ошибка попадает в HTML так же, как в JSON-поля `narrative` / `narrative_error`; текст рецензии не обрезается. |
| `--html PATH --max-findings N` | По-прежнему ограничивает только текстовый stdout. JSON и HTML содержат все находки. |
| `--html PATH --spec PATH` | В HTML попадают id/title/правила именно этой рубрики; при невалидной рубрике файл не создаётся, код 2. |
| `--html ""` | Отказ до аудита, код 2, файл не создаётся. |
| Без `--html` | Поведение полностью прежнее. |

**stdout**: байт-в-байт прежний текстовый или JSON-отчёт.
**stderr**: при успехе — ровно одна строка `HTML-отчёт: <абсолютный путь>`; при отказе — `ОТКАЗ: HTML-отчёт не записан — <причина>`; ошибки рецензии не дублируются в stderr, они остаются в JSON и в HTML.

**Коды возврата**:

| Ситуация | Код |
|---|---:|
| аудит 0/1/2, HTML записан | код аудита (0/1/2) |
| аудит 0/1/2, `--narrative` не удался, HTML записан | 3 (текущее поведение сохраняется) |
| путь `--html` отклонён до аудита | 2, аудит не запускается, отчёт не печатается |
| ошибка записи после аудита | 2, отчёт аудита уже напечатан |
| ошибка записи и недоступная рецензия одновременно | 2 (ошибка экспорта важнее) |

Код 3 не меняет вердикт аудита: в HTML остаются баллы, находки и отдельный бейдж деградации. Код 3 сохраняется и при блокере; только ошибка экспорта даёт 2 вместо 3.

**Ошибки пути `--html`** (все — до `load_spec()` и `audit()`, после `validate_all()`; ошибки target/spec имеют приоритет):

| Ситуация | Причина в stderr | Код |
|---|---|---:|
| пустая строка или только пробелы | `--html: путь не указан` | 2 |
| расширение не `.html`/`.htm` | `нужен файл .html или .htm, получено '.txt'` | 2 |
| путь указывает на существующий каталог | `<path> — это каталог, нужен файл` | 2 |
| нет родительской папки | `родительская папка <dir> не существует` | 2 |
| родитель — не каталог | `родитель <path> не каталог` | 2 |
| целевой файл — символическая ссылка | `<path> — символическая ссылка, укажите реальный путь` | 2 |
| нет прав / ошибка записи после аудита | `не удалось записать <path>: <причина>` | 2 |

`~` раскрывается, относительный путь разрешается от текущего каталога, в подтверждении печатается абсолютный. Пробелы в PATH разрешены. Родительские папки не создаются. Симлинк в родительских папках допустим, целевой файл-симлинк — нет. Путь внутри `target` разрешён. Существующий обычный файл перезаписывается атомарно; при любой ошибке прежнее содержимое остаётся нетронутым, temp-файлов не остаётся. Права результата — `0600`.

## 3. Экран HTML

Один самодостаточный файл, открывается по `file://`, без сети.

**Шапка**:
- `<h1>` «Отчёт аудита rubrica»;
- `spec id · spec title` (экранированные);
- цель аудита — разрешённый путь папки сдачи;
- метрики: `Баллы: P/M`, `Пройдено: p`, `Провалено: f`, `Блокеров: b`, `Код аудита: 0|1|2`;
- баннер вердикта: «Все правила пройдены» / «Есть провалы без блокеров» / «Есть блокирующие провалы»;
- отдельный бейдж «Рецензия недоступна» при `narrative_error`.

**Панель действий** (над списком):
- поиск `type=search`, подпись «Поиск по находкам», подсказка «rule id, заголовок или детали»;
- селект «Severity»: `все`, `blocker`, `major`, `minor`;
- чекбокс «Только провалы»;
- селект «Сортировка»: `порядок рубрики` (по умолчанию), `провалы сначала`, `severity: blocker → minor`, `rule id`, `вес: больше сначала`;
- кнопка «Сбросить»;
- счётчик `Показано N из M` с `aria-live="polite" aria-atomic="true"`.

Поиск — регистронезависимая подстрока (Unicode casefold) по rule id, заголовку и деталям; пробелы по краям отбрасываются. Фильтры и поиск комбинируются по AND. Сортировка устойчивая: при равенстве сохраняется порядок рубрики. Изменения применяются сразу, без перезагрузки страницы. Для клиентской фильтрации элементы списка несут только контролируемые атрибуты `data-severity`, `data-ok`, `data-weight` и экранированный `data-search`; динамические строки в другие атрибуты не попадают.

**Список находок** — секция «Находки», все находки в порядке рубрики, без обрезки:
- текстовый статус `PASS` / `FAIL` (не только цвет);
- бейдж severity: `blocker` / `major` / `minor`;
- rule id в `<code>`;
- заголовок правила;
- детали проверки;
- вес: `вес: N`.

**Предупреждения** — секция «Предупреждения» со счётчиком; каждый пункт отдельной строкой; если пусто — «Предупреждений нет».

**Рецензия** — секция «Рецензия», три состояния:
- `--narrative` не передан: «Рецензия не запрашивалась»;
- рецензия получена: полный экранированный текст с сохранением переводов строк, без Markdown, без обрезки;
- рецензия недоступна: «Рецензия недоступна: <narrative_error>» и фраза «Результат аудита не изменён».

**Подвал**: `rubrica · <spec_id>`. Даты и времени генерации нет; `generated_at` в модель и разметку не входит.

## 4. Состояния и пустые состояния

| Состояние | Что видно | Код |
|---|---|---:|
| Все правила прошли | зелёный баннер, `Провалено: 0`, все находки `PASS` | 0 |
| Провалы без blocker | жёлтый баннер, провалы в списке | 1 |
| Есть blocker | красный баннер, блокирующие находки выделены | 2 |
| Рецензия недоступна | бейдж деградации, блок с ошибкой, метрики не меняются | 3 |
| Блокер + рецензия недоступна | баннер блокера и бейдж деградации одновременно | 3 |
| Нет совпадений после фильтра | «Ничего не найдено. Измените запрос или сбросьте фильтры», `Показано 0 из M`, метрики прежние | как у аудита |
| «Только провалы» при полном успехе | «Провалов нет» | 0 |
| Нет предупреждений | «Предупреждений нет» | — |
| Пустой отчёт (защитный случай) | «Находок нет», `0/0`, без падения | 0 |
| Нет JavaScript | полный список и все секции читаются; панель фильтров скрыта, есть пояснение | — |

Ошибки экспорта не создают частичный HTML: либо полный файл, либо прежнее состояние пути. Ранний отказ по пути не печатает отчёт аудита; ошибка записи возникает уже после печати отчёта и не искажает его.

## 5. Доступность и офлайн

- `<!DOCTYPE html>`, `<html lang="ru">`, `<meta charset="utf-8">`, `<meta name="viewport">`, осмысленный `<title>`.
- CSP: `default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; img-src data:`.
- Семантика: `<header>`, `<main>`, `<section aria-labelledby>`, `<h1>/<h2>`, список `<ul>/<li>`; нативные `input`, `select`, `checkbox`, `button`.
- У каждого контрола есть видимая подпись через `<label for>`; у кнопки — понятное имя.
- Полное управление с клавиатуры: Tab/Shift+Tab, Space для чекбокса, Enter не перезагружает страницу; видимый фокус не менее 2 px.
- Счётчик результатов — `aria-live="polite" aria-atomic="true"`.
- Статус и severity передаются текстом, а не только цветом. Контраст текста ≥ 4.5:1, крупного текста и границ ≥ 3:1.
- Все CSS/JS встроены. Нет `<link>`, `<script src>`, `<img src>`, `@import`, `url(...)`, `fetch`/XHR и внешних URL в разметке.
- Каждая динамическая строка проходит `html.escape(s, quote=True)`; HTML из данных не исполняется; рецензия выводится как обычный текст.
- Без JavaScript отчёт остаётся полным и читаемым; фильтрация — прогрессивное улучшение.
- Одинаковый отчёт даёт байт-в-байт одинаковый HTML: без времени, случайных id, `hash()` и нестабильного порядка; файл завершается `\n`.

## 6. Функциональные требования

- **FR-UI-001**: CLI принимает `--html PATH`; флаг виден в `rubrica --help` с описанием «записать автономный HTML-отчёт».
- **FR-UI-002**: `--html` не меняет stdout и не добавляет полей в JSON.
- **FR-UI-003**: `--html` и `--json` можно использовать вместе; stdout остаётся чистым JSON прежней схемы.
- **FR-UI-004**: при успешной записи в stderr печатается ровно одна строка с абсолютным путём.
- **FR-UI-005**: HTML — один файл с встроенными CSS/JS, без внешних ресурсов; открывается офлайн.
- **FR-UI-006**: шапка содержит spec id, title, target, score/max, passed, failed, blockers, код аудита и вердикт.
- **FR-UI-007**: список содержит все находки с PASS/FAIL, severity, rule id, заголовком, деталями и весом.
- **FR-UI-008**: предупреждения показаны полностью; пустой список имеет явное состояние.
- **FR-UI-009**: рецензия имеет три состояния: не запрошена, получена, недоступна; ошибка не меняет метрики.
- **FR-UI-010**: поиск фильтрует по rule id, заголовку и деталям без учёта регистра и обновляет счётчик.
- **FR-UI-011**: severity-фильтр и «только провалы» комбинируются по AND.
- **FR-UI-012**: сортировка предлагает порядок рубрики, провалы сначала, severity, rule id и вес; по умолчанию — порядок рубрики.
- **FR-UI-013**: «Сбросить» возвращает все контролы к значениям по умолчанию и показывает все находки.
- **FR-UI-014**: счётчик `Показано N из M` обновляется при каждом изменении фильтров.
- **FR-UI-015**: пустой результат фильтрации показывает сообщение и не скрывает итоговые метрики.
- **FR-UI-016**: PATH обязателен, расширение — только `.html` или `.htm`; всё остальное отклоняется до аудита с кодом 2.
- **FR-UI-017**: пустой PATH, каталог вместо файла, отсутствующая родительская папка, родитель-файл и целевой симлинк отклоняются до аудита с кодом 2.
- **FR-UI-018**: родительские папки не создаются; существующий файл перезаписывается только при успехе.
- **FR-UI-019**: при недоступной рецензии код 3 сохраняется независимо от вердикта аудита 0/1/2; ошибка записи даёт 2 и перекрывает 3.
- **FR-UI-020**: ошибка записи даёт код 2 и сообщение с путём и причиной; отчёт аудита уже напечатан, старый файл не повреждён.
- **FR-UI-021**: при отказе входа/рубрики HTML не создаётся, код 2; ошибки target/spec приоритетнее ошибок PATH.
- **FR-UI-022**: все данные экранируются; рецензия выводится как обычный текст и не обрезается.
- **FR-UI-023**: отчёт использует `lang="ru"`, CSP, семантические элементы, подписи и клавиатурную доступность.
- **FR-UI-024**: без JavaScript отчёт читается и содержит все находки.
- **FR-UI-025**: HTML детерминирован для одинакового отчёта и флагов; `generated_at` отсутствует.
- **FR-UI-026**: `--max-findings` ограничивает только текстовый stdout; JSON и HTML всегда содержат все находки.

## 7. Критерии успеха

- **SC-UI-001**: для 100% запусков с валидным `--html` файл существует, не пуст, имеет права `0600` и открывается офлайн.
- **SC-UI-002**: 0 сетевых запросов при открытии отчёта (DevTools/Network на `file://`).
- **SC-UI-003**: score/max, passed, failed, blockers и полный список rule id в HTML на 100% совпадают с JSON того же запуска.
- **SC-UI-004**: при 200 находках любое изменение фильтра или сортировки применяется быстрее 100 мс на офисном ноутбуке.
- **SC-UI-005**: клавиатурой доступны все контролы и сброс; фокус всегда виден.
- **SC-UI-006**: HTML с недоверенными строками `<script>` и `"><img onerror=...>` не исполняет их и показывает как текст.
- **SC-UI-007**: повторная генерация из одинакового отчёта даёт идентичные байты файла, включая завершающий `\n`.
- **SC-UI-008**: все сценарии отказа PATH дают код 2, сообщение с причиной, не создают файл и не оставляют `.tmp`.
- **SC-UI-009**: при ошибке записи старый отчёт сохраняет прежние байты, а stdout уже содержит напечатанный отчёт аудита.

## 8. Допущения и границы

- HTML всегда содержит полный отчёт; скрытых по лимиту находок и поля `hidden_findings` нет.
- `--max-findings` остаётся ограничением только консольного текста; JSON не меняется.
- Расширение `.html`/`.htm` обязательно; имя файла по умолчанию не подставляется; `-` не означает stdout.
- Родительские каталоги не создаются; путь `~` раскрывается; относительный путь считается от текущего каталога.
- Запись внутрь папки сдачи разрешена: отчёт отражает состояние до экспорта, повторный аудит увидит новый файл.
- Даты генерации нет и флаг `--html-date` в эту фичу не входит.
- Новых зависимостей нет: HTML собирается средствами стандартной библиотеки; CSS/JS — простой встроенный текст.
- Не входит: автооткрытие браузера, локальный сервер, графики, Markdown-рендеринг рецензии, темы, сохранение фильтров между открытиями, локализация, изменение текстового/JSON-формата.
- Поддержка — актуальные Chrome/Firefox/Safari/Edge; IE не поддерживается.

## 9. Вопросы команде логики

**Решено общим контрактом.** Открытых вопросов нет; все прежние пункты закрыты:

1. **Гранулярность и лимит** — контракт §1 и §3: HTML содержит все находки в порядке рубрики, `hidden_findings` отсутствует, `--max-findings` режет только текст.
2. **Код 3 при блокере** — контракт §1: сохраняется текущее поведение, 3 возможен при любом вердикте 0/1/2; 2 выставляет только ошибка экспорта.
3. **Валидация пути** — контракт §2 и §4: после `validate_all()`, до `load_spec()`/`audit()`; расширение обязательно, симлинк-цель отклоняется, родители не создаются.
4. **Ошибка записи** — контракт §1, §2, §4: атомарная замена через temp + `os.replace`, старый файл цел, код 2, отчёт уже напечатан.
5. **Рецензия и детерминизм** — контракт §3: текст не обрезается, `generated_at` нет, одинаковый вход даёт идентичные байты; экранирование на слое HTML.

## 10. Изменения после согласования

1. **Лимит находок.** Было: `--max-findings` трактовался как потенциальный лимит и для HTML. Стало: HTML и JSON всегда содержат все находки, лимит — только текстовый stdout. Почему: HTML обязан совпадать с JSON, иначе сверка отчётов врёт.
2. **Расширение PATH.** Было: путь без расширения принимался как есть. Стало: обязательны `.html` или `.htm`, иначе код 2 до аудита. Почему: предсказуемый артефакт и защита от записи в произвольный файл.
3. **Момент валидации и родители.** Было: проверки пути описывались разрозненно, часть — после аудита. Стало: после `validate_all()`, до `load_spec()` и `audit()`, родительские папки не создаются. Почему: ошибки target/spec сохраняют приоритет, а плохой путь не запускает чтение сдачи.
4. **Симлинк.** Было: случай не был зафиксирован. Стало: целевой файл-симлинк отклоняется, симлинк в родителях допустим. Почему: перезапись через ссылку может изменить неожиданный файл.
5. **Код 3 и блокер.** Было: предлагалось оставлять 2 при блокере и не выставлять 3. Стало: 3 сохраняется как текущее поведение при любом вердикте; 2 перекрывает 3 только при ошибке записи. Почему: фича аддитивна, существующий контракт кодов не переписывается.
6. **Рецензия и время.** Было: в черновике логики предлагались обрезка рецензии до 20 000 символов и обсуждение `generated_at`. Стало: рецензия без обрезки, `generated_at` отсутствует. Почему: HTML = JSON и байтовая воспроизводимость.
7. **Текст ошибки.** Было: два разных префикса — `ОТКАЗ` и `ОШИБКА ЭКСПОРТА HTML`. Стало: единое `ОТКАЗ: HTML-отчёт не записан — <причина>`, подтверждение — `HTML-отчёт: <путь>` в stderr. Почему: один наблюдаемый контракт для раннего отказа и ошибки записи.
8. **Блок рецензии без флага.** Было: черновик логики предлагал не выводить блок без `--narrative`. Стало: три явных состояния, включая «Рецензия не запрашивалась». Почему: пользователь должен отличать «не просили» от «сломалось».
